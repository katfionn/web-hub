长任务不阻塞：异步子代理

一个真实体验缺陷——采购分析要 1 分钟、按钮变灰、用户被迫等待——催生了 AsyncSubAgent：把子代理的生命周期从一次请求里剥离出去，用"任务 ID + 服务 + 轮询"三件套换取主 Agent 的持续可用。最后一讲回到求职视角，倒推这条技术路线的能力清单。

P33

AsyncSubAgent 解析（一）：把"等 1 分钟"变成三条工程约束

22m38 ▼
一句话定位 从一个真实体验缺陷出发，把需求翻译成三条工程约束（后台跑 / 主 Agent 立即恢复 / 可凭 task_id 查询与取结果），并引出 AsyncSubAgent 的概念澄清。
  • 问题域收敛：采购分析要 1 分钟、按钮变灰、用户被迫等待——这是同步子代理的体验缺陷。
  • AsyncSubAgent 的"异步"与 Python 协程无关，本质是生命周期解耦；同步 subagent 像函数调用（阻塞、返回结果），异步则立即返回 job/task ID。
  • 主 Agent 以 supervisor 身份继续服务用户，并保留 send/update、cancel、list、跨轮状态、长任务、并行、中途干预等能力。
  • 机制落点：所有能力都收敛到 Agent Protocol Server（= LangGraph 本地服务，langgraph dev --host 127.0.0.1 --port 2024）。
  • 内部以 thread（会话容器）/ run（一次执行）/ state（当前状态） 三元组管理后台任务，状态机取值 running / success / error / cancelled；主 Agent 通过 5 个工具操纵它。
同步子代理                         异步子代理（AsyncSubAgent）
─────────                          ────────────────────────────
task() ──阻塞 60s──→ 结果           task 启动 ──→ 立即返回 task_id
用户界面：按钮变灰、无法继续         主 Agent 继续服务用户
                                    后台 run 跑完 → 轮询取结果
P34

AsyncSubAgent 解析（二）：改造路径与四个字段、五个工具

20m52 ▼
一句话定位 从代码层面讲解 AsyncSubAgent 的改造路径——服务侧 langgraph.json 用自定义 graph_id 注册异步图；主 Agent 侧用 AsyncSubAgent(name/description/graph_id/url) 声明。
  • langgraph dev 只需要两个必需文件：langgraph.json + pyproject.toml。
  • 服务侧：原来主智能体的键写死为 "agent"（不可改名）；新增异步条目改成自定义 graph_id（画面可辨 procurement_analyst_async）。
  • graph_id 是异步子智能体的唯一 ID，必须与主智能体侧完全一致（讲者专门截图对比两处）。
  • main_agent.py 三处改动：定义同一个 ASYNC_ANALYST_GRAPH_ID、加环境变量 ASYNC_ANALYST_URL（127.0.0.1:2024）、import AsyncSubAgent。
  • 子智能体拆成两个列表：sync_subagents = resolve_subagent_tools(...)（只留订单管理）+ async_subagents: list[AsyncSubAgent]，最后 subagents = sync_subagents + async_subagents。
  • loader 里加排除判断：采购分析的 YAML 没删但不读，否则会被同步列表重复加载。
  • 异步子智能体不能靠 YAML 配置，单独写 async_procurement_analyst.py（核心是一行 create_deep_agent(...)）。
  • 异步条目只有四个字段：name（procurement-analyst）/ description（"耗时采购分析专家……后台运行，适合长任务"）/ graph_id / url。
  • 5 个工具由 AsyncSubAgentMiddleware 提供（配置了 async subagents 就自动进默认中间件栈）。
  • create_deep_agent 只是函数名：产出物是主还是子，由代码位置决定。
  • 部署拓扑/传输可选：ASGI transport（同进程共部署）或 HTTP transport（远程），拓扑分 Single / Split / Hybrid。
工具作用
start_async_task启动后台任务，立即返回 Task ID
check_async_task查询状态 + 取结果
update_async_task发新指令（同一 thread 打断旧 run，task ID 不变）
cancel_async_task服务端 runs.cancel() 并标记 cancelled
list_async_tasks列出全部任务；非终态并行取实时状态，终态读缓存

四个易踩的坑

① update 走同一 thread 的 interrupt 策略——旧 run 被打断、带完整历史 + 新指令重启，但 task ID 不变。

② 任务元数据必须放在 supervisor graph 的专用 state channel async_tasks，与 message history 分离——否则消息被压缩后，只存在 tool message 里的 task ID 就丢了。

③ checkpoint 不指定就落在 in-memory，生产要换 MongoDB 等持久 checkpointer。

④ 主 Agent 提示词要加路由规则：采购分析 → start_async_task；操作采购单 → task；简单问候 → 直接应答；通用知识 → web_search；新偏好 → 更新偏好文件。

P35

AsyncSubAgent 解析（三）：写侧异步 + 读侧轮询的运行闭环

7m29 ▼
一句话定位 运行闭环——前端 POST → 主 Agent start_async_task → 服务建 thread/run 并立刻返 task_id → SSE 推"任务已启动" → 子 Agent 在全局沙箱里跑 → 前端每 5 秒轮询 → 完成后自动展示结果。
  • 启动编排（现场日志顺序，可直接当部署检查表）：MCP Server → 初始化沙箱 → 通过 Docker 创建容器 → 连接 MCP Server → 加载子智能体 → 启动 Agent 服务 127.0.0.1:2024。
  • 异步回执原文："采购分析任务已经启动……任务编号是 xxx……在后台运行，完成后页面会自动展示结果，您可以继续处理其他事务"。
  • 界面级差别：同步时那个位置是停止按钮、不能再问别的；异步后可以立刻让它"调用技能 / 编写新 Skill / 下载 Skill"。
  • 查状态与取消都是自然语言：说"后台任务执行情况"→ 自主调 check_async_task；说"强制杀掉"→ 调 cancel_async_task。5 个工具全暴露给主智能体，由模型做意图识别自主选择。
  • 结果自动落地：完成后页面推送"任务已完成，以下为分析结果"，与同步版结果基本一致，唯一区别是执行者换成了异步子智能体。
前端 POST /api/chat/stream
        │
        ▼
主 Agent ── start_async_task ──→ Agent Protocol Server(127.0.0.1:2024)
        │                              │ 建 thread / run
        │◀────── 立即返回 task_id ──────┘
        │ SSE: "任务已启动"
        ▼
前端每 5s 轮询 /api/async-tasks/{task_id}
                                       │
                     子 Agent 在全局 OpenSandbox 内执行
                                       │
                        完成后 state 落盘 → 页面自动展示结果
AsyncSubAgent 不是"更快的子代理"，而是把子代理的生命周期从一次请求里剥离出去，用"任务 ID + 服务 + 轮询"三件套换取主 Agent 的持续可用。
P36

AI 大模型如何基于 Harness 去找工作

12m21 ▼
一句话定位 借 DeepSeek 新开的"Agent Harness 研发工程师"岗位，倒推 Harness 方向的能力清单、技术栈取舍与简历写法（求职建议集）。
  • 岗位信号：讲者称"今年 5 月中旬"DeepSeek 官方开始面向社会+校招发布 Agent Harness 研发工程师；此前主要招算法/模型训练/算子优化方向。
  • 企业侧风向：早期用 Dify 之类搭"内容智能体"，特征是大量系统提示词、只解决单一简单任务、灵活度不够；OpenHands/Codex 这类 Harness 架构走红后，企业定制复杂业务智能体也倾向选 Harness。
  • 可投的岗位名：大模型应用工程师、大模型应用算法工程师、AI Agent 工程师、大模型工程师。
  • 能力主干：上下文工程 + 驾驭工程、Skills（尤其是 Skill 管理）、Sandbox（解决安全）、任务规划。
  • RAG 定位被下调但要学透：讲的是 Agentic RAG；海量知识库仍必须上企业级向量库（Elasticsearch、PostgreSQL+向量插件、Milvus），配套多路召回、切片优化、两轮以上重排、评估、query 重写。
  • 推理与部署：了解 vLLM / SGLang 推理核心源码；Agent 后端走 FastAPI → ASGI → Docker 多实例 → 反向代理/负载均衡。
  • 模型层基本功：神经网络与 Transformer 全流程、各类微调算法、PyTorch。
  • 框架取舍（讲者明确建议）：LangChain / LangGraph / Deep Agents 为主；LlamaIndex 不建议再花精力（尚未支持 Harness 架构）；时间充裕可看阿里 AgentScope。
  • Web Coding：Codex / Claude Code 至少会一个；会基于 Hermes/OpenHands 类成熟 Harness 做 Skill 定制与下载。
  • 微调"有概率但要会"：意图识别环节很多公司用 8B 级小模型定制微调，只干单一场景判别（讲者举例字节）。
  • 简历硬门槛：简历里必须有多智能体；RAG 若写上，必须有切片优化 + 多层索引 + 两层以上重排 + 多层评估。
  • 可抄的简历条目模板（讲者正例，恰好就是本项目）：任务规划、虚拟文件系统、子智能体委派、上下文管理、可插拔 Skills 技能系统、全生命周期记忆管理、安全沙箱、链路追踪。
简历筛的是架构词汇的证据：多智能体、切片优化、多层重排、沙箱、Skills、记忆管理，少一个就少一轮面试。

D 组小结：异步化的三件套

① 任务 ID 立即返回→ ② 服务 Agent Protocol Server→ ③ 轮询 5s 一次
层次同步子代理异步子代理
调用语义函数调用：阻塞、返回结果作业提交：立即返回 task_id
主 Agent被占用继续服务（supervisor）
状态载体tool message专用 state channel async_tasks
进程边界同进程另一进程（LangGraph / APS）
沙箱共享共享（故需健康检查 + 重建）
