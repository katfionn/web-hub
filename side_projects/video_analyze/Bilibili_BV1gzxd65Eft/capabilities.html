人工介入解析：采购 700 个火花塞，两次中断零代码

9m54 ▼
一句话定位 用"采购 700 个电装 DENSO 火花塞"的端到端演示，把 Human-in-the-Loop 讲清：第一次中断补齐缺失字段、第二次中断做订单审批，整套中断代码零开发、只靠 YAML 配置。
  • 场景起点：主智能体把任务转交给「采购订单管理」子智能体（项目有两个子智能体：采购分析 / 采购订单管理）。
  • 第一次中断——缺字段：子智能体调 request_order_info MCP 工具查订单必填字段，发现缺「预计交货日期 / 单价确认 / 订单备注」，触发 interrupt_on，前端呈现卡片式人工确认组件。
  • 卡片 UI：左列缺少字段 3 项 + 右列已收集数据 6 项 + 底部自然语言输入框。
  • 自然语言回填 + 自动提取：用户输入"预计 2026 年 7 月 30 号交货，协商单价 29 元/个，备注电装 DENSO U27ETR 铱金火花塞采购"，大模型自行解析成结构化 JSON 字段。
  • 第二次中断——审批：准备真正调 order_create 写 ERP 时触发，卡片变成"需要人工确认以下操作" + ✓同意 / ✗拒绝。
  • procurement_order.yaml 里配 interrupt_on: order_create / order_update，各带 allowed_decisions: ["approve","reject"]。
  • interrupt_on 是讲者自研 DSL 而非框架原生：自写 loader.py 把 YAML 翻译成 LangGraph 的 interrupt_on 节点配置。
  • allowed_decisions 是白名单：拒绝后不调工具、不写库；同意后才真正调 MCP 工具。
触发人工介入的代码你都不用写，这是最牛的地方。只要在你的 YAML 配置文件里，你需要触发人工介入在哪个地方，你配上去就行了。

Sandbox 解析（一）：安全边界、作用域隔离与预热

20m46 ▼
一句话定位 把项目最大亮点——基于 OpenSandbox 的安全边界，从"为什么必须有沙箱"讲到"防护三件事 + 用户作用域隔离 + 预热机制"，并现场启动三件套用日志证明时序。
  • 问题引入：Skill 要么项目预置，要么从网上下载（魔搭社区 Skills 中心、ClawHub），企业项目免不了用外部 Skill。
  • 两类安全风险：脚本含恶意代码（Python / Node.js / Go / Java 都可能有）；多用户文件必须隔离。
  • 为什么不只靠权限判断：权限判断只能解决读写权限问题，系统命令的安全性很难判断，所以干脆把所有风险行为放进"铜墙铁壁的盒子"里运行。
  • OpenSandbox：阿里云 2025 年 12 月开源的容器管理项目，用它做所有 Skill 执行、命令执行、文件操作的安全边界兜底。
  • 防护三件事：宿主机文件系统不可见（容器内 /skills/、/data/ 是容器自己的）／进程隔离（execute() 的进程在容器内）／资源限制（cpu:"2"、memory:"4Gi"）。
  • 沙箱内运行环境：Python / Go / Java / Node.js 四种；所有 Skill 脚本、系统命令、HTTP 请求（web-scraper）、web 抓取都在这里跑。
  • 墙内 / 墙外：墙外（宿主机 Windows）＝ FastAPI、MongoDB、MCP Server；墙内（容器 Linux）＝ /skills/、/data/、/analysis/、/memories/、/AGENTS.md、/workspace/。
  • 两个附加机制：用户作用域隔离（每个用户一个沙箱，张三/李四互不可见）+ 沙箱预热（登录即备好空闲沙箱，被占用后立刻补建下一个）。

Sandbox 解析（二）：五个 py 文件如何拼成一个沙箱

19m45 ▼
一句话定位 从代码层面解析沙箱创建链路、命令执行链路、故障热替换恢复、预热-认领-补充时序、用户作用域隔离的实现。
  • 核心结论：沙箱就是 5 个 py 文件层层包装出来的——底层直接怼 Docker、中层把 SDK 翻译成框架协议、外层只做"一个永远不变的引用"。
  • 用户手里拿的永远是 proxy，容器可以在背后被换掉。
  • 创建链路：sandbox_setup.py → setup_sandbox(config, sandbox_id=None, image=None) → SandboxSync.create(image, entrypoint=["/opt/opensandbox/code-interpreter.sh"], env={"PYTHON_VERSION":"3.11"}, resource={"cpu":"2","memory":"4Gi"}, timeout=timedelta(hours=2), connection_config=config) → 返回 OpenSandboxBackend。
  • entrypoint 决定容器里有哪些语言环境；timeout 定生命周期上限（超时自动回收）。镜像必须预先放在服务器本地镜像库。
  • 健康与故障：SandboxHealthMiddleware 每次 before_agent ping；失败则重建，连续失败交给熔断中间件（#1/#7 双保险）。
  • 时序：启动建空闲沙箱#1 → 张三登录认领#1 → 日志"正在创建新沙箱" → 空闲#2 就绪 → 李四认领#2 → 再补#3……企业可一次预热 5/6/10 个。
  • 结果印证：创建沙箱时上传 13 个基础文件；/analysis/ 等目录都在容器内。

自我进化的 Skills（一）：四阶段生命周期

19m44 ▼
一句话定位 用"一句话让智能体下载并装配新 Skill、立刻可用、自动持久化"的完整演示，引出 Skill 的四阶段生命周期：同步 → 渐进式发现 → 运行时创建/下载 → 分配与持久化。
  • Skill 两类来源：① 项目预置（开发期写好）② 运行时新增（用户下载或 Agent 生成）。
  • 执行与存储的分离：所有 Skill 都在 OpenSandbox 中执行（安全），都持久化到 MongoDB/StoreBackend（永久）。动机：沙箱用完即销毁，容器一回收里面文件全没。
  • 阶段 1 同步到沙箱：把本地预置 Skill 上传到沙箱（增量 + _seed_files 首次）。
  • 阶段 2 渐进式发现：每个智能体有独立 Skill 目录，通过中间件做发现。
  • 阶段 3 运行时自动创建/下载新 Skill：母 Skill（skill-management）负责。
  • 阶段 4 分配与持久化：把 Skill 分配到任意子智能体（复制到对应 scope 目录），并持久化到 StoreBackend。
  • 演示一：复制 Skill URL → "帮我下载这个 Skill 地址，分配给采购分析" → 母 Skill 自动下载、结构校验、功能测试、分配、清理临时文件 → 立刻可用。
  • 演示二：用户描述"读取并解析 Excel 文件" → 母 Skill 自动创建 SKILL.md + 脚本 → 安装依赖、语法检查、生成模拟测试数据、功能测试 → 询问分配到哪个子智能体。
  • 企业价值：功能增加/需求改变 = 增删 Skill，Skill 甚至不需要人写。
  • 母 Skill 内部自带 R2T（ReAct + Task Planning）四步：写 SKILL.md 与脚本 → 装依赖并测试 → 分配与持久化 → 清理临时文件。

自我进化的 Skills（二）：三个中间件 + 母 Skill + assign_skill

11m47 ▼
一句话定位 把演示背后的代码架构讲清：三个中间件（SkillsMiddleware + SkillsSyncMiddleware + UserSkillsRestoreMiddleware）+ 母 Skill + assign_skill 工具。
  • SkillsMiddleware —— Deep Agents 框架自带，负责渐进式披露。
  • SkillsSyncMiddleware —— 自定义，负责本地 src/skills/ ↔ 沙箱同步（增量 + _seed_files）。
  • UserSkillsRestoreMiddleware —— 自定义，负责StoreBackend ↔ 沙箱同步（新沙箱创建时恢复已持久化 Skill）。
  • 渐进式披露的 token 账：每个 SKILL.md 的 frontmatter 一般 ≤200 token、最大 2000；100 个 Skill × 200 ≈ 2 万 token；DeepSeek-V4 上下文百万级，几乎无压力——所以启动只加载元数据，需要时再 read_file 加载全文。
  • 完整 SKILL.md 较长时采用分页加载，不一次性塞入上下文。
  • assign_skill：自定义 @tool，本质是"移动目录"——从 main/ 移到目标子智能体 scope 目录，并同步到 StoreBackend。
  • Scope 映射：每个子智能体对应一个 scope，scope 对应沙箱 /skills/{scope}/；主智能体默认 scope 是 main。
  • 自我进化流程：获取（URL 下载 / 描述创建）→ 沙箱内测试 → 通过则分配+持久化、不通过则自动修复 SKILL.md 再测 → 分配到 scope 目录 → 被 SkillsMiddleware 自动发现。
  • 讲者特意试过让 Agent 生成更复杂的 Skill、故意让测试不通过，Agent 会自己修复 SKILL.md 直到通过。
  • 教学定位：不是教"如何用 Skill"，而是教企业级项目里 Skill 的全生命周期管理。

Context-Engineering（一）：四流程与三种压缩

14m21 ▼
一句话定位 从"上下文工程 ≠ 提示词工程"切入，讲四流程（输入 → 压缩 → 隔离 → 长期记忆）与压缩的三种机制，并用 CompositeBackend 路由代码演示 /memories/ 的落点。
  • 区别：提示词工程只关注"怎么写好 system prompt"；上下文工程关注"怎么把正确的信息在正确的时机送到 Agent"——包括输入组装、压缩、隔离、长期记忆。
  • a. Input Context：提示词 + 工具描述 + Skills 元数据 + 用户偏好。
  • b. Compression：三层压缩机制（自动 85% 阈值 / 手动 compact / 子智能体隔离）。
  • c. Isolation：多智能体之间上下文完全隔离，天然降低单次调用体积。
  • d. Long-term Memory：/memories/{user_id}/preferences.md + StoreBackend 持久化。
  • 自动摘要 85% 阈值：达到 max_input_tokens 的 85% 触发；触发时 ① 把完整历史写入文件持久化 ② 调大模型总结，用总结替代原历史。
  • 手动 compact：通过 Deep Agents 的 create_summarization 得到一个"摘要工具"，Agent 可自主决策调用——因为自动摘要在"正在处理重要数据"时强行触发会丢语义。
  • 提示词里写明时机：AGENTS.md 里显式写"在收到子智能体长篇报告时主动调 compact"。
  • 子智能体隔离 = 天然压缩：就算不做摘要，最终调模型时上下文也天然变小；交接格式写在系统提示词里。
  • 路由实证：/memories/ → StoreBackend，命名空间由 runtime.context['user_id'] 决定（namespace=lambda rt: (rt.runtime.context.user_id,)）。

人工介入详解：两层中断与 SSE 恢复闭环

18m07 ▼
一句话定位 Human-in-the-Loop 的两层中断（代码级 interrupt() + 配置级 interrupt_on）与 SSE 恢复闭环。
  • 本项目只在下采购单时触发；触发点由程序员决定，写在代码或配置里。
  • 第 1 层——数据完整性补全：自写工具 request_order_info 内部第 33 行调 interrupt()，把"缺失字段 + 已收集数据"抛给前端；可收任意补充信息，灵活。
  • 第 2 层——最终审批：interrupt_on: order_create / order_update，allowed_decisions: ["approve","reject"]，执行前暂停，只能同意/拒绝，克制。
  • 两层互补：自写工具用 interrupt()（灵活）；调他人工具用 interrupt_on（克制——多只能填太多反而易错）。
  • chat.py 第 300+ 行遍历流式 chunk 的 interrupts，按类型 yield 一条 type="interrupt" 的 SSE 消息：action_requests → hitl_approval；order_info_request → 数据补充。

SSE 事件流：StreamingResponse + 生成器 yield

17m59 ▼
一句话定位 用 FastAPI + StreamingResponse + Python 生成器实现 SSE，把流式输出、工具调用、人工介入中断三类事件统一封装成前端可消费的 text/event-stream。
  • 6 大能力复盘：Planning / 文件后端 / Multi-Agent / 上下文管理 / Skills / Human-in-the-Loop。
  • 文件后端边界：普通文件后端 / 数据库文件后端不能执行命令，只有 OpenSandbox 与 local shell 能——Claude Code / OpenClaw / Harness 默认用 local shell。
  • 为什么是 SSE：企业级智能体必须流式输出；可勾选/取消"显示工具调用"。
  • FastAPI 是主流：VLLM / SGLang 等推理框架内置 FastAPI；启动文件加载 CORS 中间件。
  • chat.py 三大视图：chat_stream（流式对话）、chat/{thread_id}/resume（中断恢复）、get_chat_history（普通 JSON，查 MongoDB）。
  • 响应头：media_type="text/event-stream" + Cache-Control: no-cache + Connection: keep-alive + X-Accel-Buffering: no。
  • SSE vs WebSocket：SSE 单向（服务端 → 客户端），比 WebSocket 轻量，足够智能体场景。
  • 生成器 + yield：每次 yield 推一帧；for chunk 遍历，按 chunk_type 分支（interrupt / messages / tool）。
  • 前端不同图标/边框颜色（黄=工具，蓝=AI），可过滤显示。
  • 双流模式：流 A messages + 流 B values（中断检测），中断检测必须在 messages 处理之前。
async def chat_stream(request: ChatRequest):
