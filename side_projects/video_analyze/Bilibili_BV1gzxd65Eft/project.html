大模型岗位分类和 Harness Agent 项目

18m38 ▼
一句话定位 用"面试官要看多智能体 + Harness 架构"的就业判断，引出企业级项目 ERP_OPENCLAW 的外部依赖全景。
  • 求职方向二分（主观分类）：① 大模型研究方向 / 预训练（985 硕士起）② AI 大模型工程化落地（应用开发、微调、推理优化、传统算法如 YOLO）。
  • 面试新要求两条：智能体里有没有多智能体、有没有 Harness 架构。
  • 项目定位：基于已有 ERP 系统的智能采购助手，不是玩具 demo，要和老系统对接。
  • 前后端：前端 Vite + Vue（:3000），后端 FastAPI（:8090）；智能体跑进 ASGI 服务，两个理由——异步高并发、真正实现流式输出（SSE）。
  • 与 ERP 的对接方式：MCP 协议 + 网关读取 Java ERP 数据，不直连数据库。
  • 两类安全诉求催生沙箱（本质 Docker 容器）：Skills 可能含安全隐患；多用户文件必须隔离。沙箱服务 OpenSandbox:8080，需要镜像仓库预置多套镜像。

项目外部依赖全景

前端 Vite:3000（Vue SPA） → /api/* → FastAPI:8090 Chat Backend：创建 Agent Graph / 创建管理沙箱 / 读写会话。

模型 DeepSeek（api.deepseek.com）、智谱 AI（open.bigmodel.cn），另有 Web 搜索。

MCP Server:8000（Agent MCP 网关）：代理 8 个 ERP API → Java ERP:8080（采购业务），另提供 26 种图表工具。

云服务器（39.100.100.28）：OpenSandbox:8080、MongoDB:27017、摩托车配件商城:80（供应商报价页面）、镜像/包仓库（阿里云容器镜像 + PyPI）。

P16

Harness 驾驭工程的概念

10m48 ▼
一句话定位 把"提示词工程 → 上下文工程 → 驾驭工程"讲成一条包含关系的演进线，并给出 Agent = Model + Harness 的公式与它要解决的五个工程病。
  • 三阶段：提示词工程 2022–2024；上下文工程 2025 年 2 月之后；Harness Engineering（驾驭工程）2026 年 2 月之后。
  • 三者是包含关系：驾驭工程 ⊃ 上下文工程 ⊃ 提示词工程。
  • 今天单讲提示词没意义：新智能体的提示词不固定，随上下文、随每个用户的偏好运行时动态注入。
  • 定义：Harness 不再只优化模型输出，而是"构建包裹在模型之外的一整套系统化基础设施"，把不确定的智能转成可靠、稳定、能长时间执行复杂任务的工作引擎。
  • 新能力只有一个词：长周期复杂任务。对比"明天上海天气"（一句话调工具）与"统计 2026Q1 全部涉案账户并分析其特征"（先拆清单再执行，可能调 7–8 个工具 + 3–5 个 skill）。
  • 术语本义：Harness = 马具/缰绳，指"模型本身之外的所有东西"——工具、记忆、规划、安全护栏。
  • 出处：LangChain 团队一篇约 126K 访问量的文章，精炼成 Agent = Model + Harness。
  • 传统 Agent 的五大工程难题：上下文窗口爆炸、状态丢失、工具调用混乱、缺乏规划、无法从失败中恢复。
P17

Harness 架构的 Planning 能力

14m12 ▼
一句话定位 用"简单任务 vs 复杂任务"的对照演示，把 Planning 落到 write_todos 这一个工具上——它既做拆解，也做状态追踪。
  • 简单任务不需要规划：问"你有哪些可用技能/工具"，直接调工具即答，不生成 todo。
  • 复杂任务样例：把"摩托车火花塞"与"博世火花塞"做采购综合对比分析——没告诉它对比维度，正是需要规划的场景。
  • 复杂任务第一步是子智能体预判，随后模型调 write_todos 生成任务清单。
  • 清单固定 6 步：扫描技能目录并加载分析手册 → 收集规格参数 → 市场价格调研 → 供应商渠道对比 → 执行对比分析并生成图表 → 输出报告到 /analysis/；每步带 status，初始只有第 1 步 in_progress。
  • 执行中清单被反复重写：末段时前 5 步 completed、第 6 步 in_progress——规划 = 拆解 + 逐项状态追踪两件事。
  • 报告落在沙箱内 /analysis/，下载走 download/；报告里的柱状图、表格、雷达图是现场生成（数据来自网搜 + ERP）。
  • write_todos 入参里那段"流程"不在代码里，而在 skill 的 md 文件中定义：理解需求 → 收集数据 → 执行分析 → 生成图表 → 生成报告，只定大阶段。
  • 持久化：CHECKPOINTER（MongoDBSaver） 持久化 Agent state，跨重启保留任务进度。
P18

解析任务规划 Planning 能力

15m30 ▼
一句话定位 从代码层拆 write_todos——它内部再调一次推理模型生成清单，再用 LangGraph 的 Command 把清单写进 graph state 的独立字段。
  • 底座是 DeepAgents 框架（LangChain 团队，依赖 langchain 1.2 + langgraph 1.1），官网首句即"面向 Agent 的 Harness 框架"。
  • write_todos 本身不"算"清单，而是再调一次大模型（推理模型）生成。
  • Planning 的五层核心：① 目标分解与结构化 ② 状态驱动的执行循环 ③ 动态重规划与自我修正 ④ 执行诊断与可解释性 ⑤ 长时任务的抗遗忘机制。
  • 执行循环里每一步可能走 MCP 工具（查 ERP），也可能走网页抓取 skill——skill 与 tool 都能被 todo 驱动。
  • 出错即自我修正：某步执行不了就重新生成新的任务项，并做意图识别。
  • 抗遗忘：清单固化在 state 里且不允许被摘要、剪裁——占 token 很少，但能防止长任务"忘了做到第几步"。反证：Claude Code / Codex 的 compact 摘要后确实会"遗忘"。
  • 关键实现：清单不写进 messages（会被压缩），而写进 state 另一个固定 key；写入方式是 Command(update=...)（全量替换 state["todos"]，并附一条 ToolMessage("Updated todo list")）。
P19

Harness 架构的文件后端解析

13m13 ▼
一句话定位 文件后端不是一个目录，而是"可插拔的抽象层 + 按路径路由"——本项目用 CompositeBackend 把 /memories/、/skills/ 和其余路径分给两个不同的后端。
  • 文件后端 = 文件的全套操作：增、删、改、查、执行。
  • 写在主智能体里，不在子智能体里；因为后端不做智能体间隔离，所有智能体共享同一套文件后端（隔离交给沙箱）。
  • 实现是 CompositeBackend，内部挂了 3 个后端：sandbox_backend（default）+ store_backend（两条路由）。
  • 路由规则：/memories/ → store_backend；/skills/ → store_backend；其余全部 → default → sandbox_backend。两条路由必须显式拆分，否则与 default 冲突。
  • 实例验证：/analysis/xxx.md 不属两条路由 → 落到沙箱；docker exec 进容器，根目录下果然有那个 md。
  • store_backend 的数据落在哪由 LangGraph 的 store 决定；项目用默认 InMemoryStore，换 Redis/MongoDB/Postgres 就落到对应库。
  • 抽象层意义：文件后端不代表真有文件系统——可能是容器、KV、Redis、MongoDB；本地 OS、内存字典都能当文件后端。
  • 文档族谱：StateBackend（仅一次执行线程内有效）/ FilesystemBackend（本地磁盘）/ LocalShellBackend / StoreBackend / CompositeBackend / 自定义后端。
路径                              → 目标后端
/memories/{user_id}/...           → StoreBackend（LangGraph store）
/skills/{scope}/...               → StoreBackend（持久化技能）
其余（/analysis/ /data/ /workspace/）→ SandboxBackend（OpenSandbox 容器）

Harness 架构的 Multi-Agent 解析

18m12 ▼
一句话定位 多智能体的难点不是"拆几个 Agent"，而是上下文隔离下的任务委派；本项目把委派压缩成"提示词定格式 + 大模型抽取 + task() 转交"，并把子智能体做成 yaml 零代码弹性加载。
  • 多智能体天然是父子/主从结构，且不止两层——子智能体本身还能当主；多层要靠预编译子图实现。
  • 核心前提：所有子智能体之间上下文完全隔离，A 不知道 B、B 不知道 A——这才是委派存在的理由。
  • 委派 = 从 A 的上下文里"截取"一部分数据传给 B；载体是一个叫 task 的工具。
  • 工程化改造：把"要抽哪些字段"写进提示词，再由大模型从 A 的上下文抽取成结构化文本。
  • 抽取 5 项：任务目标、用户编号、分析需求正文、输出要求、重要提醒；task 的 description 参数就是抽取后的成果。
  • 反向（B 返回 A）同理：返回格式写在 B 自己的配置里——谁提供数据，格式就定义在谁那边。
  • SubAgent 弹性加载：全项目 1 主 + 2 子（analyst＝供应商比价/行情分析/策略建议/市场调研；order＝创建修改采购单/订单查询/数据补充），两个子 Agent 一行代码都没有，只有 yaml。
  • yaml 字段：name、description、可调用 tools 列表、skills 目录列表、system_prompt，另有需人工确认的工具列表（interrupt_on 就配在这里）。
  • 加载链路：load_subagent_configs() 读 configs/*.yaml 并校验 4 个必填字段 → resolve_subagent_tools() 用子串匹配把字符串映射成实际工具对象、合并 extra_middleware → create_deep_agent(subagents=...)。
  • 扩展方式：新建一个 yaml 丢进 configs/ 即可，Python 侧零改动；主智能体 reload/热启动生效。
