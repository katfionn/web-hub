P01

Harness 是什么：一条命令跑起来你的第一个 AI 工位

10m ▼
一句话定位 从官网 slogan 讲到两种启动方式，给后续源码精读定下前提——先把工程跑起来。
  • 入口是官网：deepseek.com/harness。开发者预览版，面向全球开发者开放测试。
  • 唯一前置依赖是 Node.js。npx @deepseek-ai/dsh web 一条命令跨平台启动（默认端口 3080）。
  • 源码安装：git clone → pnpm install → 构建 → pnpm dsh web --port 8080。安装版与源码版要错开端口。
  • 启动入口在 apps/cli/src/bin.ts，讲者在此加了一行 running from source 调试日志用于区分启动方式。
  • 时间成本：首次装依赖 2–5 分钟、构建 5–10 分钟、启动 2 分钟内；第二次显著加快。
P02

一切皆插件：四种预设模式怎么选

13m27 ▼
一句话定位 用设置页把"一切皆插件"落地，给出四种 Agent 预设的选型口径；末尾给出读源码的方法论框架。
  • 设计哲学：所有带 Agent 能力的东西都是插件——模型、工具、Skills、会话、沙箱、存储、循环、调度、UI 本身；插件之间通过服务 + 事件对话、自由拼装。
  • 默认 159 个插件，每项都能搜、能配。
  • 标准：功能最全的编码 Agent，日常开发用它。
  • PTC：继承标准 + Code Mode SDK，让模型用一个 TypeScript 程序组合多步操作；适合"需求模糊但明显是长任务"。
  • 极简：只给 bash + str_replace_editor 两个工具，适合做基准测试/压测。
  • 创造：继承标准 + 运行时检查 + 插件实验 + preset 创作指导。
  • 边界规则：预设变更"对此后新建的会话生效，运行中的会话保持它开始时的预设"。
  • 模块三问（读源码的总纲）：① 它声明了什么 ctx.* 服务？② 它发出 / 监听什么事件？③ 它注册了什么 effect（可逆副作用）？
  • 源码阅读路线：入口 → 插件树 → 会话 → prompt 组装 → 工具 → Agent 与主循环(Agent-Loop) → 模型 → END；其中 Agent-Loop 与模型是循环体。
  • 插件 ≠ 工具：插件是"注册了什么能力"，工具是"某次会话实际挂上去、model 能调的"。159 个插件，但一次对话经 prompt 组装后实际可能只有 3 个工具。
P03

读源码第一步：入口在哪、插件树怎么叠三层

7m17 ▼
一句话定位 按 P02 的路线落地第一步与第二步——找到 bin.ts 入口、看清插件树的三层加载顺序。
  • 入口的朴素方法：bin 目录 = 启动目录，即 apps/cli/src/bin.ts。
  • bin.ts 结构：readVersion() → parseDshArgs(process.argv.slice(2), ...) → switch (invocation.mode) 分派到 profile / plugin / dump-config / default 四种模式。
  • profile 分支：先 loadLayeredEnv('dsh') 分层加载 .env，再 runProfile(...) 按 profile 起插件。
  • 插件树三层加载，永远后者覆盖前者：① 自身/内置的默认插件集；② profile 目录里的插件；③ 用户主目录 ~ 下的插件/配置。
  • 想覆盖默认行为，不必改源码，在用户目录写一份同 ID 的配置/插件即可。
P04

对话信息藏在哪：session 事件驱动与持久化归属

10m+ ▼
一句话定位 读第三个模块 session，得到全课第一个"颠覆认知"的结论——flush 不是持久化，会话语义只在内存，落盘是插件的事。
  • 会话代码不在 apps 里，在 packages/core/session/src/index.ts，1000 多行。
  • 文件结构顺序：import → 类型/接口声明 → SessionStorage 接口 → interface Events（把会话事件声明成"事件名 → 回调签名"）→ 工具类型 → 校验与组装函数。
  • 四个核心事件： session/created（创建）/ session/disposed（销毁/离开 store）/ session/event（追加后广播，post-commit、fire-and-forget）/ session/flush（awaited parallel durability checkpoint）。
  • session/created / disposed / event 都受 @deepseek-ai/dsh-scope 的 scope 过滤：agent 级监听器只看得到"经由该 agent context 进入"的会话。
  • 最大的认知点：这些事件全在内存。flush 只打一个检查点，并不落盘；真正的持久化由持久化插件承担（插件列表里能找到名字带 storage / storage-json 的"持久化三件套"）。
  • 为什么要检查点而不是随时存：模型输出可能只到一半，此时落盘会把残缺状态写进去；恢复时从中间状态续接会改变对话规则/思路。
  • 方法论引申：传统读源码的直觉（看到 flush 就以为"刷盘了"）会被"一切皆插件"打破——会话自己只负责内存日志。
P05

提示词与工具链：像 AOP 一样的三层拦截机制

9m39 ▼
一句话定位 落到两个最常被二次开发的插件——system-prompt（提示词组装）与 tools（工具调用 + 三层 AOP 式拦截）。
  • 提示词组装位置在 packages/core/system-prompt，入口 src/index.ts；system-prompt 自身也是个插件。
  • Cordis 内核只干一件事：插件的加载、卸载、依赖关系；其余"模型/工具/技能/会话/沙箱/存储/循环/调度/UI"全是插件。
  • 插件 ≠ 工具：插件是大容器，内部包含若干工具；工具被调用时一定经过三层拦截（AOP 式），每层以事件形式暴露。
  • tools/pre-execute（before）：@mode waterfall，可放行/拒绝/询问。
  • tools/execute（executor）：@mode waterfall，围绕派发的 timeout/retry/metrics。
  • tools/post-execute（after）：@mode waterfall，可接受/替换/富化/拦截结果。
  • @mode waterfall 是 Cordis 的事件模式之一：按注册顺序依次执行，上一环可以把结果传给下一环（next() 决定是放行还是替换），与 Java Spring 的 AOP / 拦截器链、Servlet Filter 链思路一致。
  • 关键不变量：exec.signal 是调用方取消信号，任何替换层都不能脱开调用方的取消。
P06

Agent 与 Agent Loop：主循环七步怎么跑起来

10m01 ▼
一句话定位 把"一切皆插件"落到最核心的两个插件 agent 与 agent-loop，解释为什么要把"智能体是什么"和"智能体的循环怎么跑"拆成两个插件。
  • 两个插件：packages/core/agent/src/index.ts 与 packages/core/agent-loop/src/index.ts。
  • agent 插件定义"智能体是什么"（接口、注册表、agent state、create agent、事件总线）；属于静态描述层。
  • agent-loop 插件负责"把这个智能体跑起来"（think → read → write → think → …）；属于运行时驱动层。
  • 拆开动机（讲者）：主循环要能被不同预设（标准 / PTC / 极简 / 创造）复用与替换，不该焊死在智能体定义里。
  • Web UI 一次"你能做什么？"对话的轨迹能看到 Glob → Think → Pwsh → Think → Read → Pwsh → Think → Read，并显示"3轮·9步 | LLM 1m15s · 工具调用 10.4s | 首 token 平均 1.1s · 103 tok/s | 缓存命中 79% | 输入 149K tok · 输出 6.7K tok"。
  • 七步主流程：① 源码入口 bin.ts → ② 加载三层插件树 → ③ 日志 + 存储初始化 → ④ 用户输入 → ⑤ prompt 组装 + 工具装配 → ⑥ Agent Loop 主循环（think → 工具执行 → think → …） → ⑦ LLM 调用 → END。
P07

大模型调用怎么实现：抽象适配与环绕事件

10m44 ▼
一句话定位 把主循环里每一圈 think 的最终落点——调大模型——拆到 packages/core/llm，得到"抽象类适配器 + waterfall 环绕事件"的可插拔结构。
  • packages/core/llm 提供抽象适配器（provider/model/reasoningEffort/流式回调等），各家模型是子类实现。
  • LlmRuntime extends Service：对外暴露 stream(options: GenerateOptions): AsyncIterable<StreamChunk>；内部先走 streamWithRegistration，最终落到 this.ctx.waterfall(this, 'llm/stream', options, () => this.adapterStream(options, prepared))。
  • llm/stream 事件是"环绕每一次流式调用"的 waterfall，所有模型调用都经过这个单一事件，再调到 adapterStream（生成器函数，token 级 delta 流）。
  • 这个 waterfall 挂的三大能力（讲者归纳）：重试机制 / 回放机制 / 路由机制——全部以监听器形式挂在 llm/stream 上，所以换供应商、改重试策略都无需改 LLM 调用源码。
  • PreparedLlmCall 接口：把"一次调用的 config + adapter registration"一起解析好并深冻结，字段包括 config / retryPolicy / context / adapterDefaults；保证一次调用的配置与适配器注册强绑定、不可变。
  • 请求冻结：buildRequest() 用 deepFreeze(structuredClone(...)) 冻结请求，确保"请求到底该不该发出去"经过一系列组装与条件判断。
P08

主循环（回合 turn）× 事件总线

19m43 ▼
一句话定位 把 ReactLoopAgent.turn() 当"唯一主线"读完——turn 在外、while 在内，一切状态变化都落成 session.append(...) 事件；再补 cordis 的 waterfall 事件总线如何把插件串成责任链。
  • 主循环路径：packages/core/agent-loop/src/agent.ts，类 ReactLoopAgent implements Agent，246 行 private async turn(): Promise<boolean>。
  • turn() 骨架（帧实证）：不在运行态就直接抛错 → signal.throwIfAborted() → const turn = phase.turn + 1 → session.append('turn/start', { turn }) → while (true) { ... } → preStep() → step() → finally 写回合结束 + reason。
  • turn 与 step 的关系（讲者用拳击打比方）：一个"回合"=一场拳击的一局，step = 局内出拳；"只要拳速够快、够准，一个回合里打 100 次都行"——所以 while 在 turn 里面，不是 turn 在 while 里面。
  • preStep() 三件事：① 认领输入（从 inbox 取 target）② 组装提示词 ③ 瀑布流调用 → decision。preStep 才是"插件真正插手的地方"。
  • step() 流式调用模型，每个 chunk 都 session.append 落盘，所以"中间这些思考过程全部被持久化了"。
  • 事件总线（vendor/cordis/src/events.ts）：parallel（并发）/ emit（同步）/ serial（串行直到一个 listener bail）/ waterfall（把最后一个 dispatch argument 当成 innermost next，listener outermost-first，不调 next() 就否决整条链）。

RAG 答案为什么会"飘"

10m04 ▼
一句话定位 学员提问"RAG 智能问答怎么让答案稳定不漂移"，讲者给出向量检索 → 知识图谱（GraphRAG）→ 记忆/MCP 的加固路径，并用自家"学习助手"的迭代史演示落地节奏。
  • 问题拆解：① RAG 企业知识库的基础做法就是向量检索；② 要让答案稳定，要加知识图谱（GraphRAG）。
  • 为什么必须加图谱："不建图谱，大模型始终是概率事件"——向量只解决"内容相似"；图谱补的是"知识之间的关系"。
  • 举例（课程域）：直播课 27 期 → 课时 → 建关系（包含、前置、并列）。查询走 prerequisite 链，"哪个课有哪些章、哪些知识点、之前要先学什么，一目了然"。
  • 落地案例「学习助手」：RAG + 知识图谱 + function/finetune 都在用，提问时还做了记忆增强。
  • 迭代史：需求设计 → V2 加知识图谱并升级 Harness 架构 → V3 从 demo 级网页改成对接 Web 协议 → 用真实学员群灰度测试 → 后续继续加 MCP。
  • 方法论（反复强调）：做智能体不要一上来就做到 90%–95%，要先与主业务系统联调，一步两步三步迭代。
P10

插件四件套 + MCP 对接

9m53 ▼
一句话定位 一次"认知翻转"——源码精读最难，插件开发最简单；一个插件的最小形态 = cordis.yml（声明）+ src/index.ts（四件套）。
  • 插件最小形态 = 两个文件：cordis.yml（声明 id + name）与 src/index.ts（代码入口）。
  • 四件套（lesson4-example-tool/src/index.ts 全文实证）： ① 固定引入 Context + defineTool； ② 插件命名 export const name = 'tool-student-local'； ③ 声明硬依赖 export const inject = ['tools']； ④ 挂载入口 export function apply(ctx: Context)，内部 ctx.tools.register(defineTool({...}))。
  • 注册体五要素：name / description / parameters / output.schema / execute。
  • 完全体（MCP 插件）：四件套不变，多出 Config 与错误映射——interface Config { url; apiKeyRef; toolCallTimeoutMs } + 同名 zod schema 运行时校验；toDiagnostic() 把协议错误翻成"人话"。
  • MCP 接入细节：用官方 MCP SDK（Client + StreamableHTTPClientTransport），凭证经 ctx.credentials.resolve(config.apiKeyRef) 解析、不进代码。
  • 讲者结论：复杂的插件前面全都一模一样，只是多了一个 config、多了一堆 MCP 端点引入与协议错误诊断——入口始终是 apply。
