Chapter 02 · 核心理论（P1 讲授段 + 课程文档）

为什么单元测试不够用

"非确定性系统怎么测？"——这是整门课要拆掉的第一堵墙。讲师从软件工程史讲起（单元测试 → 回归测试 → A/B 发布），逐个说明为什么这套方法论在 LLM 应用上逐层失效，最后交付一个替代结构：数据集 + 评委 + 实验。

2.1悖论：熟办法撞上陌生系统

"We have this notion of how software is built and tested — unit testing, regression testing… But now: how do we test non-deterministic systems? What can we do when these things drift at different layers of the stack? It's a very conflicting image."— 讲师，P1 03:07 – 03:45（意译）

课程文档把冲突写得更直接（Unit 1 · 文档原文）：

"Classic code is deterministic — execute the same code and you get the same output. So tests are typically just assertions… LLM-powered applications are inherently non-deterministic… The same prompt can produce different outputs. Unlike traditional software, which is deterministic and easy to test with assertions, LLM behavior is intrinsically unpredictable. You need more than pass/fail on a golden test case."

— 课堂文档 "Introduction" 节（P1 164:54 屏幕原文整理）

2.2单元测试的四条边界（文档原文）

局限原文在 Agent 场景里的具体表现
输入输出必须预先给定"Accepts predefined inputs and outputs"一条用户消息可以有很多合理回复，golden answer 写死哪个都是错的
断言是静态硬编码"Hardcoded / static assertions""回复里必须含订单号"这类断言无法表达"先认证后答复"的流程合规
维护成本随规模爆炸"Cheap to run, difficult to maintain at scale"100 条断言好维护，1000 条场景 × 多轮对话就不可持续
捕捉不了定性质量"Doesn't capture qualitative aspects"语气、helpfulness、是否解决诉求——恰恰是用户体验的核心

替代品：eval 的正式定义

"The process of creating a train set for your model is similar to creating a test set for your model. Evaluation, then, is the process of measuring an LLM-powered application on different performance characteristics (quality, safety, security, reliability, cost, latency, etc.) against that dataset. We can't begin improving our apps unless we can quantify our current performance."

— 课堂文档 "Introduction" 节；评分维度清单意味着评估从不是"一个分"，而是一张多维度体检表

2.3再往上：A/B 测试也救不了

就算你把单元测试换成了"线上 A/B"，问题依旧。入门视频里的论证链（重建见 图表 03）：

噪声大

"Too noisy — requires massive sample sizes." 对话质量指标的方差让显著性检验需要海量流量。

归因粗

p=0.04 只告诉你"v2 均值更好/更差"，不告诉你差在退款场景还是上下文丢失。

迭代慢

每周都要发版的团队等不起 A/B 跑完显著性——评估必须能离线、按场景、几分钟出结果。

2.4替代结构：三腿凳（课堂一手证据）

讲师在 P1 讲授段直接把凳子搬了出来："You remember the three legs picture? Recall your metrics — you have the jobs to be done（任务）, what are the metrics, how we will score them."（P1 150:16，完整重绘见 图表 01）三条腿缺一条，"your basic eval is incomplete"（P1 151:01）。

其中第二条腿——指标——在课上被拆成两个桶：

AI 指标

质量分、准确率、faithfulness……描述"回答本身好不好"。学员在课上共同答出的双桶结构（P1 152:03）。

业务指标

解决率、升级率、留存、情绪分……描述"对业务有没有用"。讲师提醒：dashboard 全绿而用户在 Reddit 骂街，就是只有 AI 指标没有业务指标（P1 160:55）。

2.5阈值是场景的函数，不是拍脑袋的数字

讲师的真实经历，两个极端：

内部员工 Agent：50% 就够了

"Internal only, I can do a more controlled launch… as long as it's passing 50% on quality and accuracy scores, I was okay to launch it internally."（P1 152:21）——低风险、可灰度、错了能立即回滚。

法务 / 财务 Agent：90%+ 加双保险

"Where the cost of being wrong is very high… 90% plus, and also with citations, and also with some deterministic checks on top."（P1 153:09）——高成本错误 + 确定性兜底 + 引用可查。

决定"评估强度"的三维模型（P1 175:25 手绘三框讲解的重绘）

2.6两条被反复强调的原则

原则一：Eval 先行——"在动手构建之前"

"You should be doing it before you even start building, or even building your first prototype. Otherwise the number of iterations you would need will be very high."— 答学员 Naveen 问"eval 在开发流程中的位置"，P1 173:03（意译）

他的落地演示：假设明天要上线一个"卖冰淇淋"的新 Agent——先写数据集/测试场景/failure modes → 拿着这份"评估规格"去 vibe code 原型（"this is what I'm building, these are the guardrails I need"）→ demo → 收集反馈 → "what about this metric? what about sentiment score?" 补进评估。评估清单本身就是更好的提示词与 PRD。

原则二：Eval 驱动的不止产品，还有 GTM

"We talked about eval-driven PRD. Another important thing is eval-driven go-to-market, eval-driven selling, eval-driven marketing."（P1 162:32）逻辑很朴素：B2B 客户会问"你的 Agent 凭什么比 OpenAI/Google 的好"——如果你手里有分场景的评测结果，销售就有的聊、官网就有得写。他指出模型厂商发布新模型时都在这么干，"if you build on top of models, you need to take the same approach"。

2.7局限：这不是银弹

评估≠全知

课程大纲专门有 "Limitations" 一节：评委本身会错、数据集会过时、离线评估模拟不了全部真实分布——所以要有业务指标兜底与灰度发布。

"Evals are not free"

算力、标注、平台额度都是成本；这也是课程争取 Braintrust credits、并强调"先跑 5 条也行"的现实原因。

本章小结：单元测试 → 只能测确定性；A/B → 太吵太慢太粗；三腿凳 → 可重复、可分层、可自动化。接下来就看第三条腿怎么落地——CH03 的 Week 1 实战。
