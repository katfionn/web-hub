Chapter 03 · 视频主线

Week 1 实战：Trace → 标注 → 错误分组

这是整门课最重要的一周作业——不是因为技术难，而是因为它刻意去掉了所有技术难度。没有 LLM 调用、没有复杂框架，只有一个脚本化客服 Agent 和 40 条真实感的对话。你要练的肌肉是：看见问题、说清理由、归类分组。

3.1为什么 Week 1 故意"不调用 LLM"

"Week 1 is bounded on purpose… the skill I want all of you to build before you go too far is: the ability to look at a trace, see what's wrong, annotate it, and group your observations."— 讲师，P2 13:05（意译）

很多学员的第一反应是"这不真实"——对话都是 agent.py 里的正则与固定回复，问"我的订单呢"它就去翻 ticket，没接任何模型。讲师两次解释了设计意图：

统一可跑性

"Some of you may not have your LLM API set up, that's why I'm waiting for Braintrust."（P2 06:00）所有人先在自己的机器上把流程跑通，不因环境差异卡死。

先建"人眼"再建"机器眼"

"The goal is not to be 100% correct at this point… the need to understand fundamentals will never go away, no matter how these logs are showing up."（P2 17:11 / 34:12）

配套的 harness 是公开 GitHub 仓库（讲师演示时直接 clone 到 Cursor 里）：make setup 装依赖 → make agent 启动客服 Agent → 输入问题得到回复与 trace。"Once you have the make agent completed, then that agent will be ready to take your inputs."（P2 24:08）——学员 Roger 在 Mac 上卡在 make agent，讲师的诊断是依赖/版本问题，建议把完整报错贴给 AI 助手："they are all pretty much the same, then they will tell you how to fix it."

3.2作业七步动线

Step 1

跑通 Agent

make setup → make agent；确认单轮问答能出结果。失败多为 pip 依赖 / Python 版本（P2 20:49）。

Step 2

生成 traces

用仓库自带的 demo 数据跑一批对话；多轮对话可以一次传入多个 turn（P2 24:26 "you can literally pass multiple turns in here"）。

Step 3

接入可观测平台

拿到 Braintrust（或 LangSmith）的 SK_ 开头 API key → 写进 .env → traces 自动流入平台。一次埋点，终身受益（P2 29:16 / 25:40）。

Step 4

逐条读、逐条标

打开 Chat Transcript 看对话，进 span 看工具调用；对每条给 pass / fail，并写下理由（failure 的原因类别）。

Step 5

把标注写回 CSV

作业的交付物是标注好的 CSV。多轮会话每轮一行，不要把多轮用逗号塞进一个单元格（P2 59:50 学员踩坑复现）。

Step 6

分组统计

"Out of 40 examples, how many had issues related to refund, how many related to…"（P2 13:38）按失败类型聚簇，得到一张"问题分布表"。

Step 7

看 9 分钟 solution 视频

课后发布的 walkthrough：setup → error analysis → 明确列出已知局限（如 stateless harness 丢上下文）。"My goal is not to share this beforehand… try it out first."（P2 69:42）

3.3没人告诉你的 Pass/Fail 判定哲学

学员 Uma 的困惑非常典型：一条对话里 Agent 反问"请提供订单号"，而用户已经说了"同一订单被扣两次 $62.10"。这算 pass 还是 fail？讲师现场打开 demo 数据跑了一遍，然后给出判例：

"From the workflow standpoint… first you want to authenticate the user and make sure this is the right person. If it's asking for order ID, then this is the correct behavior. So you'll call it a pass."— 讲师，P2 16:18（意译）
判定三原则
① 站在业务工作流上看行为是否合规（先认证、再动数据）；
② 不同标注者可以判得不一样——先写清理由，再求一致；
③ 这阶段的一致性目标是"可讨论"，不是"绝对正确"。
失败归因要分两层
学员 Naveen 发现"上下文丢失、没有 agent ID"——讲师确认这是 harness bug（脚本化 harness 无状态），不是产品 bug：
"That will be harness bug, because it's just the way this harness has the limitation… that's the right term to use."（P2 63:42）

标注时顺带记录的信息

字段为什么记
pass / fail最终的二元判定，用于统计通过率与回归基线
失败类型（refund / warranty / context / tool…）错误分组的分组键；决定"下一步修什么"的输入
失败发生在哪一层（LLM span / tool call / 会话）把问题定位到代码或提示词，而不是"整体不好"
harness bug 标记环境问题不计入产品指标，避免误导后续优化

3.4常见坑（全部来自本场答疑的真实提问）

坑 1 · 多轮 CSV 格式：输出只剩最后一轮
学员 Hian 的标注 CSV 中，输入用斜杠分隔多轮，但输出只保留了最后一轮，需要回到 trace 里重新拼。讲师回复：多轮应作为独立的轮次行提交，而不是逗号拼接在单格里；格式不对会导致 join 失败。他当场把正确示例补进了 repo README。（P2 59:50 – 61:46）
坑 2 · "这不算真实数据，我能改吗？"
"Don't fix it on the full correctness or not."（P2 16:55）——本作业要的是标注肌肉，不是修 Agent。想玩真的：用 Cloud Code / 自己的框架建一个真 Agent，把 trace 接到同一个平台即可，课程不复刻那个 harness。
坑 3 · Braintrust 要下载整个项目吗？
"No, you don't need it on the Braintrust. That's your running — in my case locally."（P2 29:56）平台只接收 traces，不托管代码。
坑 4 · 拿不到 API 额度 / 不想花钱
讲师的顺序建议：先用平台 credits（他争取到了 $10–20）；预算敏感可用本地小模型（Ollama），但注意"20 条用例要 10–20 分钟"，只适合小批验证。（P2 02:01 / 28:45）
坑 5 · 想跳过标注直接调 LLM Judge
不行——Week 2 的 Judge 对齐需要 Week 1 的人工标注当"人类共识"的基线。"That's why the exercise we did in week one: you take the traces and then we annotate them."（P2 10:26）没有标注，Judge 没有校准锚点。
