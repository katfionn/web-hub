Chapter 04 · P2 36:00–46:00 精讲

读 Trace 与多轮评估

"这个日志看起来好乱"——所有人的第一反应。讲师用了整整十分钟带学员逐层拆一条 trace，给出了一套可复用的阅读顺序。这一章把它整理成清单。

4.120/80 阅读法：先人话，后细节

"The most important thing is: start with the chat transcripts… because that's the 20/80 analysis."— 讲师，P2 36:17

顺序永远是：① Chat Transcript（这轮对话到底聊了什么、用户要什么）→ ② Root Span（整个 turn 的顶层执行）→ ③ LLM Span（模型看到了什么、输出了什么、花了多少）→ ④ Tool Calls（走了哪条路径、参数对不对）→ ⑤ Raw YAML/JSON（需要全量细节时）。

为什么要 20/80：80% 的失败在 chat transcript 就能看出来（答非所问、上下文丢失、幻觉）；只有剩下的 20% 需要下沉到 span 级去找根因（"it took the right path or wrong path"）。先看细节会被噪声淹没、"这日志看起来好乱"就是这么来的。

4.2Span 里必须看的六个数

Tokens

例中单次调用 23 tokens——异常少说明系统提示词没进来，异常多要查上下文堆叠。

Latency

总耗时（例：0.9s）。Agent 场景要按 span 逐层加总看时间去哪了。

首 Token 时间

"Time to first token"——用户体感的起点；Agent 变慢时优先查这里（P2 38:04）。

Cost

平台按 span 计费统计；也是"把 eval 跑在夜间"的动机之一。

Tool 调用链

层级结构（hierarchical threading）：哪个工具、什么参数、返回什么——失败的黄金证据。

Input / Output 全文

"what was the input, what was the output"——所有高层视图都只从这份数据派生。

4.3多轮对话怎么评：逐轮 + 整体

讲师的原话："You need to do both — each turn level, and the final pass/fail。因为会话级的 pass/fail 是：用户的问题解决了吗。"（P2 17:52，意译）

多轮里 context 是一条不断累积的链："the context keeps on building from the first question to the second"（P2 45:05）。所以逐轮定位"从哪开始跑偏"，会话级判定"最终意图是否达成"。学员 Hian 的 CSV 问题恰好暴露了多轮数据的工程约束——每轮必须独立成行，带上会话 ID 以便回拼。

与 LLM Judge 的衔接：Week 2 的 Judge 可以先做 turn-level rubric（每轮按 pass/fail 标准打分），再做 conversation-level rubric（整体是否解决）；两级 rubric 的判据要分开写，混在一起会让评委"平均主义"，把关键轮次的失败抹平。

4.4换平台会不会白学？不会

讲师现场把同一套概念在 Braintrust 与 Agentforce 里各讲了一遍：同一会话的 input、topic、action、attributes——

"Some of these attributes and naming can be vendor specific… the fundamentals are the same."— 讲师，P2 44:21

Agentforce 的 Preview 里，"小聊（small talk）"与"退款请求"走的是不同动作与工具，trace 把每一步都记下；他甚至指出厂商会给概念起不同名字，但映射关系是稳定的（见 术语映射表）。
